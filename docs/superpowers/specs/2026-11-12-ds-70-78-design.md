## Part 1 — seven small tasks (approved in chat as written)

### DS-77 — `Button` `loading`

- New prop `loading?: boolean` (default `false`).
- Visual: the children stay rendered but `visibility: hidden` so the button
  keeps its width; a `CircularProgress size="sm"` (indeterminate,
  `aria-hidden`) is centred over them. Spinner centring uses the sanctioned
  internal-anchor pattern (`position: relative` on the button, grid-stack or
  equivalent for the overlay; no consumer-visible layout props).
- Behaviour while loading: `aria-disabled="true"`, clicks ignored (the
  consumer's `onClick` is not called), stays focusable and in the tab order
  (NOT the native `disabled` attribute).
- AT (Hard rule 10, `transient-state-a11y` skill): the accessible name is
  unchanged; a visually hidden polite live region (`role="status"`), rendered
  unconditionally while the component is mounted, announces a new i18n
  string (e.g. `button.loading` → "Loading…" / "Загрузка…") when `loading`
  turns true and clears when it turns false. Same shape as `Switch`'s
  `switch.busy`. `aria-busy` alone is explicitly insufficient.
  _Builder's call settled:_ the region renders only when the `loading` prop
  is passed (`loading !== undefined`, either value), so ordinary Buttons get
  no `role="status"` node. Gating on the prop (not the state) is the
  sanctioned shape (cf. `PasswordInput`'s caps-lock region).
- Works with `as="a"`: clicks are prevented (`preventDefault`) while loading.
- `iconOnly` + `loading`: the icon is hidden, the spinner replaces it.

### DS-70 — `Rail.Item` badge visible when collapsed

- When the rail is collapsed and `badge != null`, draw a small dot at the
  icon's top-right corner (colour: the accent/attention token used by
  `Badge`'s default tone — add a rail component token for it).
- The consumer's badge node stays in the DOM and in the accessible tree:
  in collapsed mode it is visually hidden (visually-hidden clip pattern),
  NOT `opacity: 0`, so the item still reads e.g. "Emails, 3 unread".
- No count in collapsed mode (the badge is an arbitrary node; scaling it is
  fragile). Update the JSDoc on `badge` (currently says "fades to invisible").
- Applies to top-level items; items inside a `Rail.Group` flyout keep their
  expanded rendering.

### DS-71 — `Chart` `includeZero`

- New prop `includeZero?: boolean` (default `true`). With `false` on `line`
  / `area`, the y domain is the min/max of in-view values plus finite
  reference lines, then `.nice()` — no forced 0. Degenerate (all equal)
  keeps the existing `min === max` widening.
- Ignored (dev warning not required) on `bar` / `stacked-bar`: bars must
  start at 0. _My call:_ also ignored on `area` — Chart's area is always
  stacked and its fill means "from 0"; a cut baseline would lie. So the
  prop is effectively `line`-only; the JSDoc says so.
- Not in scope: an explicit `yDomain` on Chart; separate axis/tooltip
  formatters (the side ask). File the formatter ask as a new DS task.

### DS-72 — `ScatterSeries` `shape` + `emphasis`

- `shape?: 'circle' | 'square' | 'triangle'` (default `'circle'`), applied
  to every point of the series, in the plot and in the legend swatch.
- `emphasis?: 'default' | 'strong'` (default `'default'`). `strong` draws
  unsized points larger with a ring (surface-coloured outline) so they read
  over other dots and reference lines; sized points keep their size scale
  but get the ring. Word matches `ScatterReference.emphasis`.
- Radii come from tokens (`--scatter-dot-*`), read via `readPx` like the
  existing min/max.

### DS-73 — `ScatterSeries` `connect`

- `connect?: boolean | { maxGap: number }`. `true`: a solid line in the
  series colour through its visible points sorted by x. `{ maxGap }`: the
  line breaks between neighbours whose x distance exceeds `maxGap` (x units;
  ms on a time scale).
- The line is decorative (`aria-hidden`); legend, tooltip, keyboard and table
  stay per point. Hidden series hide their line. Drawn under the dots.

### DS-74 — `Chart` `integerValues`

- `integerValues?: boolean` (default `false`). y ticks are whole numbers
  only, step ≥ 1: a 0–1 range ticks 0, 1; 0–3 ticks 0, 1, 2, 3. The domain
  is nice'd so its ends land on integer ticks.

### DS-76 — `Chart` `selectOn`

- `selectOn?: 'drag' | 'tap'` (default `'drag'`); only meaningful when
  selection is on.
- `'tap'`: a mouse click or touch tap (no drag, no long-press) selects the
  nearest category as `{ from: i, to: i }` via `onSelectedRangeChange`;
  a tap on the already-selected single category clears it (`null`) — the
  toggle is the phone's only way to clear (decided with the user). Tapping
  a different category while a range is selected replaces it with that one
  category. Drag / long-press range selection still works. Tooltip
  behaviour is unchanged (the tap still inspects).
- Keyboard: Space toggles the inspected category the same way; Escape
  clears (as today). Enter keeps its current meaning (`onPlotDoubleClick`).
  _My call:_ Space-to-select works in `'drag'` mode too: it is the only
  single-category keyboard selection and costs nothing extra.
- `'drag'`: today's behaviour exactly (tap outside the band clears).

## Part 2 — DS-75 `LaneChart` (new component)

### Why

Home Hub's Effects explorer compares 3–6 measures (food grams, poo events,
weight, meds, cleanings …) over 30–90 days on a phone, to see what changes
together. Today it stacks separate `Chart`s: plots start at different x
(gutters sized per chart), x labels repeat, each chart has its own tooltip,
selection and tab stop, and events are drawn as fake count bars. `Chart`'s
docs say "different units → two charts", and two charts don't line up.

### Goals

- Several measures, each with its own y scale and unit, on one shared,
  pixel-aligned x axis.
- Feels like one chart: one tab stop, one inspected category, one tooltip
  listing every lane, one selection, one zoom/pan viewport.
- Usable on a phone at 90 categories (via the shared viewport).

### Non-goals

- Several series inside one lane, stacking, comparison series.
- A dual y axis.
- A legend (lane labels name the measures).
- Forking `Chart`'s interaction code.

### Anti-goals (a failure even if it "works")

- N `Chart`s glued together (N tab stops, N tooltips).
- Two drifting copies of selection / gesture / keyboard code.
- Any regression in `Chart`.

### Public API (decided)

New sibling component, exported like `ScatterChart`:

```ts
<LaneChart
  label="Effects, last 90 days"          // accessible name, like Chart
  categories={days}                      // string[], shared
  lanes={[
    { key: 'food', label: 'Food', type: 'bar', values, formatValue: g },
    { key: 'poo', label: 'Poo', type: 'dots', values: counts, formatValue: String },
    { key: 'w', label: 'Weight', type: 'line', values, formatValue: kg,
      includeZero: false, referenceLines: [{ value: 3800, label: '30-day avg' }] },
  ]}
  markers={markers}                       // ChartMarker[], drawn through all lanes
  selectedRange / defaultSelectedRange / onSelectedRangeChange / selectOn
  viewport / defaultViewport / onViewportChange / zoomGestures
  onPlotDoubleClick
  emptyMessage footnote
/>
```

Lane shape: `{ key, label, type: 'bar' | 'line' | 'dots', values:
(number | null)[], formatValue, includeZero?, integerValues?, color?,
referenceLines?, annotations? }`. `curve` per line lane is the builder's call
(default smooth like Chart). Same controlled/uncontrolled conventions and
same types (`ChartRange`, `ChartViewport`, `ChartMarker`,
`ChartReferenceLine`, `ChartAnnotation`, `ChartPlotPointerEvent`) as `Chart`.

- `dots` lane: a dot on each category whose value is `> 0`; no y axis; the
  tooltip shows `formatValue(value)`. `null`/0 = nothing. Decided with the
  user: presence only — a count of 3 looks the same as 1; the magnitude is in
  the tooltip and table. One dot size (scatter dot token).
- _My call:_ LaneChart also takes `zoomRange` / `defaultZoomRange` /
  `onZoomRangeChange` (with Chart's "Zoom to selection" / "Reset zoom"
  controls) and `details`, because the extracted shell carries them anyway and
  zoom-to-selection is the natural phone flow at 90 days. The shell keeps
  them as-is, so nothing in `Chart` becomes optional.
- _My call:_ in LaneChart every marker label is drawn in one shared top
  gutter (top placement); a `labelPlacement: 'beside'` is treated as top.
- Lane types reuse Chart semantics: `bar` always includes 0; `includeZero`
  / `integerValues` as in DS-71/74.
- Per-lane `referenceLines` and `annotations` behave as in `Chart`, inside
  that lane.

### Layout (my calls, approved)

- One SVG, lanes stacked vertically, one shared left gutter = the widest
  tick label across all lanes, so every plot shares left/right edges and
  category x positions.
- Lane label sits above its plot, top-left (no horizontal cost on phones).
- `dots` lanes get a short fixed height (token); other lanes split the
  remaining height equally. Fills its container like `Chart`.
- x labels once, under the bottom lane.
- Markers: lines/bands span all lanes; marker labels drawn once at the top.

### Interaction (decided)

- One focusable plot element (one tab stop), keyboard inspection as in Chart
  (arrows move the inspected category across all lanes).
- One tooltip for the inspected category listing every lane's label and
  formatted value (null → the existing "no data" treatment).
- Selection: same model and gestures as `Chart`, including `selectOn`.
- Shared viewport: wheel / pinch / pan / drag zoom anywhere moves every lane.
- `onPlotDoubleClick` as Chart; `value` reports `null` (no single y).
- Data-table fallback: one row per category, one column per lane.

### Implementation direction (my call, approved)

Extract `Chart`'s interaction shell (selection, gestures, keyboard
inspection, tooltip positioning, viewport state, table toggle) out of
`Chart.tsx` into shared internals used by both `Chart` and `LaneChart`. Reuse
`computeLayout` per lane with a forced shared gutter and x labels
suppressed on all but the bottom lane (add the minimal inputs needed, e.g.
a fixed `left`). Existing `Chart` tests must pass unchanged; they are the
regression net for the refactor. Exact module boundaries are the builder's
call.

### Component checklist (root CLAUDE.md core invariant)

Tests (pure layout in `*.test.ts`, wiring in `*.test.tsx`), playground
`LaneChartDemo.tsx` wired into App route, `navItems.ts`, `ComponentsIndex`,
`overviewSchematics`, `ComponentName` union; `src/index.ts` exports;
`docs/components/LaneChart.md` + `AI-PRIMER.md` line; CLUSTERS entry in both
`_meta/manifest.ts` and `scripts/generate-manifest.mjs`, then
`npm run build:manifest`. Update `Chart.md`'s "two measures → two charts"
guidance to point at `LaneChart`.

### Left to the builder

Token names/values for lane heights and gaps, the exact tick-count per lane,
how `dots` dots are sized (should match scatter dot tokens), module split of
the extracted shell, lane `color` default (palette slot by lane index).

## Part 3 — synced hover across charts (`ChartSync`, new; added mid-brainstorm)

### Why

Dashboards (GCP-style) stack several charts over the same period. Hovering a
moment in one should show where that moment is in every other chart, so the
reader can compare without lining things up by eye.

### Decided with the user

- Scope: every chart with an x axis — `Chart`, `LaneChart`, `ScatterChart`.
  (`DonutChart` / `FunnelChart` have no x axis and don't take part.)
- API: a `<ChartSync>` wrapper component. Every x-axis chart inside it joins
  the group; a chart opts out with `sync={false}`. No module-level state; two
  `ChartSync`s on one page are independent; nested `ChartSync` = the nearest
  one wins.
- Key: `Chart` and `LaneChart` get an optional
  `categoryValues?: (number | Date)[]` — the x each category stands for
  (e.g. the day's start), same length as `categories`. With it they sync by
  value (scatter included); without it they sync only with other category
  charts, by matching the category label exactly.
- Echo in the other charts: a vertical crosshair at the matching x, the
  marks there highlighted (line/area point dots, bar tint, scatter points in
  the bucket), AND each chart's own tooltip for that x (the user first chose
  "no tooltip", then asked for tooltips too). Every chart in the group shows
  its values at once, GCP-style.

### My calls

- What broadcasts: any inspection — mouse hover, touch tap/inspect, keyboard
  arrows. It clears on pointer leave / blur / Escape.
- Payload: `{ source, label?, from?: number, to?: number }`. A category chart
  with `categoryValues` sends its category's `[value_i, value_{i+1})` (the
  last bucket reuses the previous step); a scatter sends its point's x as
  `from === to`. A category chart receiving a value inspects-echoes the
  category whose bucket contains `from`; a scatter receiving a bucket draws
  the crosshair at `from` and highlights points with x in `[from, to)` (or
  `=== from`).
- Matching x outside a receiver's domain or current viewport → the receiver
  shows nothing (it does not pan).
- The echo is visual only: echoed tooltips and crosshairs are `aria-hidden`,
  with no live-region announcement and no focus change in other charts (a
  screen-reader user is in one chart; the source chart's own tooltip/
  announcements are unchanged).
- An echoed tooltip uses the receiver's normal tooltip placement at the
  matched category / nearest point. A scatter receiver with no point in the
  bucket shows the crosshair only (no empty tooltip). Tooltips that would
  fall offscreen are the existing tooltip's clamping problem, not new logic.
- Re-render cost: the sync value lives in a context the charts subscribe to;
  a hover must not re-render the consumer's tree (store + subscription, e.g.
  `useSyncExternalStore`, not a `useState` in the provider).
- `ChartSync` renders no DOM of its own (fragment + context), so it does not
  affect layout.

### Non-goals

- Syncing zoom/viewport or selection across charts (ask later if wanted).
- Syncing across separate React roots.

### Component checklist

`ChartSync` is a new public component: full core-invariant checklist (tests,
`ChartSyncDemo` wired in all playground files, `index.ts` exports, docs page
+ AI-PRIMER line, CLUSTERS entry in both manifest maps). `categoryValues` and
`sync` get JSDoc and docs in `Chart.md`, `LaneChart.md`, `ScatterChart.md`.
Tracked as a new DS task.
