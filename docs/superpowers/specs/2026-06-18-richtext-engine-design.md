# RichText engine (Slice 1) — Design

**Date:** 2026-06-18
**Status:** Approved (brainstorming)
**Package:** `@eocrm/design-system`

## Goal

Build the foundation of an in-house WYSIWYG rich-text capability — **our own engine**, no editor libraries (ProseMirror/Slate/Lexical/TipTap are banned by the dependency policy, the same reason Prism is playground-only). This is the long-deferred rich-text primitive the design system has promised (`AGENTS.md`: _"Rich text editing (bold, lists, mentions) → no shipped primitive; defer to a `RichTextEditor` when one exists"_).

WYSIWYG is several subsystems. This spec covers **Slice 1 only**: the pure document model + transform functions ("first small functions"), plus a thin read-only renderer shipped as a public `<RichText>` component so the model is visible on screen.

## Scope: the full slicing (context)

| Slice                                 | What                                                                                                       | Status        |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------- |
| **1. Engine core + read-only render** | Pure model (blocks + inline runs + marks), pure transforms, read-only `model → React`, public `<RichText>` | **This spec** |
| 2. Serialization                      | model ↔ HTML (and/or markdown)                                                                             | later         |
| 3. Editable rendering                 | model-position ↔ DOM-selection mapping                                                                     | later         |
| 4. Input layer                        | contentEditable (or custom) events → transforms                                                            | later         |
| 5. `<RichTextEditor>`                 | commands + toolbar + the editable public component                                                         | later         |

Slice 1 is fully usable on its own: `<RichText>` displays stored rich content in read-only CRM contexts (activity feeds, comments, audit views). The engine modules it sits on are the foundation every later slice builds on.

## Feature scope (the model's vocabulary)

**Standard CRM rich text.** Block types: `paragraph`, `heading` (H1–H3), `bullet_item`, `ordered_item`, `blockquote`, `code_block`. Inline marks: `bold`, `italic`, `underline`, `strike`, `code`, `link`. No tables/images/mentions in this scope (tables would force a recursive node tree; everything here fits a flat block model).

## The document model

A document is a **flat, ordered list of blocks**. Each block carries inline content as **runs** (text + a mark set). Marks are a per-run array, kept in a **normalized canonical form**: no two adjacent runs share an identical mark set, and there are no empty runs (except a single empty run representing an empty block).

```ts
interface RichDoc {
  blocks: Block[];
}

type BlockType =
  | 'paragraph'
  | 'heading'
  | 'bullet_item'
  | 'ordered_item'
  | 'blockquote'
  | 'code_block';

interface Block {
  /** Stable id → React keys + position stability across edits to other blocks. */
  id: string;
  type: BlockType;
  /** Heading level, only for type 'heading'. */
  level?: 1 | 2 | 3;
  /** List nesting depth (0-based), only for 'bullet_item' / 'ordered_item'. Flat items, no tree. */
  depth?: number;
  /** Inline content. A 'code_block' holds a single unmarked run (plain text). */
  inlines: Inline[];
}

/** A run of text sharing exactly one mark set. */
interface Inline {
  text: string;
  marks: Mark[];
}

type MarkType = 'bold' | 'italic' | 'underline' | 'strike' | 'code' | 'link';
type Mark =
  | { type: 'bold' }
  | { type: 'italic' }
  | { type: 'underline' }
  | { type: 'strike' }
  | { type: 'code' }
  | { type: 'link'; href: string };

/** A point in the document: a character offset within a block. */
interface Point {
  blockId: string;
  offset: number; // 0..blockLength(block)
}

/** A selection / span. `anchor` may be before or after `focus`. */
interface Range {
  anchor: Point;
  focus: Point;
}
```

**Decisions:**

- **Flat blocks, not a recursive tree.** Lists are items with a `depth` number; the renderer reconstructs `<ul>/<ol>` nesting. (A tree is only needed for tables, which are out of scope.)
- **Marks normalized** so equality is trivial and rendering is deterministic. Flags carry no data; `link` carries `href`.
- **Positions are `{ blockId, offset }`**, not a single global integer — stable across edits elsewhere and easy to unit-test.
- **Stable string block `id`s** for React keys and position mapping. Ids are generated by the constructors (a module-local counter / injectable id factory — NOT `Math.random`/`Date.now`, which are unavailable in some contexts; the constructor takes an optional `id` so callers/tests can pin ids).

## The transform functions (built bottom-up)

All functions are **pure and immutable**: `(input) → newOutput`, never mutating arguments. Layers A–C are the literal "first small functions"; Layer D composes them into editing operations. Document transforms return `{ doc, selection }` (the new doc + where the caret/selection should land).

### Layer A — mark helpers (`engine/marks.ts`)

Operate on a `Mark[]`:

```ts
marksEqual(a: Mark[], b: Mark[]): boolean        // order-insensitive set equality (incl. link href)
hasMark(marks: Mark[], type: MarkType): boolean
withMark(marks: Mark[], mark: Mark): Mark[]       // immutable add (replaces same-type, e.g. new link href)
withoutMark(marks: Mark[], type: MarkType): Mark[]
toggleMark(marks: Mark[], mark: Mark): Mark[]      // add if absent, remove if present
```

### Layer B — inline-run helpers (`engine/inlines.ts`)

Operate on an `Inline[]`:

```ts
runsText(inlines: Inline[]): string                            // concatenated text
runsLength(inlines: Inline[]): number
normalizeInlines(inlines: Inline[]): Inline[]                  // merge adjacent equal-mark runs; drop empty runs; guarantee ≥1 run
sliceInlines(inlines: Inline[], start: number, end: number): Inline[]   // extract char sub-range [start,end)
mapMarksOverRange(inlines: Inline[], start: number, end: number, fn: (marks: Mark[]) => Mark[]): Inline[]
                                                              // split runs at boundaries, apply fn to marks in range, re-normalize
```

### Layer C — position helpers (`engine/position.ts`)

```ts
blockLength(block: Block): number
findBlockIndex(doc: RichDoc, blockId: string): number          // -1 if absent
clampPoint(doc: RichDoc, point: Point): Point                  // clamp offset to [0, blockLength]
comparePoints(doc: RichDoc, a: Point, b: Point): -1 | 0 | 1    // document order
isCollapsed(range: Range): boolean
orderedRange(doc: RichDoc, range: Range): { start: Point; end: Point }   // start ≤ end
```

### Layer D — document transforms (`engine/transforms.ts`)

```ts
insertText(doc, point: Point, text: string): { doc; selection: Range }
deleteRange(doc, range: Range): { doc; selection: Range }
splitBlock(doc, point: Point): { doc; selection: Range }            // Enter: split into two blocks at point
mergeBlockBackward(doc, blockId: string): { doc; selection: Range } // Backspace at block start: merge into previous
applyMark(doc, range: Range, mark: Mark): { doc; selection: Range }
removeMark(doc, range: Range, type: MarkType): { doc; selection: Range }
toggleMark(doc, range: Range, mark: Mark): { doc; selection: Range } // toggles based on whether the whole range already has it
setBlockType(doc, blockId: string, patch: Partial<Pick<Block,'type'|'level'|'depth'>>): { doc; selection: Range }
```

Behavior notes:

- `insertText` inserts into the run at `point`, inheriting that run's marks (typical editor behavior); re-normalizes.
- `deleteRange` across blocks merges the partial first + last blocks; collapses selection to the start.
- `splitBlock` on a list item / heading produces a same-typed continuation block (Enter in a list continues the list); on a `code_block`, **Slice 1** keeps it simple and still splits into two blocks (multi-line-in-one-code-block behavior is a later refinement, documented as out of scope).
- `toggleMark` is "active" iff **every** character in the range already carries the mark; then it removes, else it adds.
- `setBlockType` changes `type`/`level`/`depth` in place, preserving inline content.

### Constructors (`engine/model.ts`)

```ts
createBlock(type: BlockType, text?: string, attrs?: { level?; depth?; marks?: Mark[] }): Block  // generates id
emptyDoc(): RichDoc                                    // one empty paragraph
docFromText(text: string): RichDoc                     // splits on \n into paragraphs (seed for demos)
```

Id generation: a module-local monotonic counter via a small `nextId()` helper, with `createBlock` accepting an optional explicit `id` so tests pin deterministic ids. No `Math.random`/`Date.now`.

## Read-only render (`engine/renderDoc.tsx`)

`renderDoc(doc: RichDoc): ReactNode` — pure mapping, used by `<RichText>`:

- **Blocks → elements:** `paragraph`→`<p>`, `heading`→`<h1|h2|h3>` (by `level`), `blockquote`→`<blockquote>`, `code_block`→`<pre><code>`.
- **Lists:** a grouping pass turns runs of consecutive `bullet_item`/`ordered_item` blocks into `<ul>`/`<ol>` with `<li>` children; increasing `depth` nests a child list inside the preceding `<li>`. The model stays flat; rendering reconstructs the tree.
- **Inline runs → tags by marks**, in a **deterministic nesting order** (`link` outermost, then `bold`, `italic`, `underline`, `strike`, `code` innermost) so output is stable and diff-friendly: bold→`<strong>`, italic→`<em>`, underline→`<u>`, strike→`<s>`, code→`<code>`, link→`<a href>`.
- Block `id` is the React `key`. An empty doc renders nothing.

## Public component (`RichText.tsx`)

```tsx
<RichText value={doc} />
```

- `forwardRef` to the root element; spreads remaining `HTMLAttributes` (Pattern A — consumer wins) onto the root; merges `className`.
- Renders `renderDoc(value)` inside a root element that owns prose styling.
- Read-only: no editing, no selection handling (that's Slice 3+). Props: `value: RichDoc`, plus passthrough (`className`, `id`, `aria-*`, …).
- Full JSDoc (Rule 7) incl. `@remarks` "when NOT to use" (e.g. for plain text → `<Text>`; for editing → `<RichTextEditor>` when it ships) + anti-patterns.

## Styling (`RichText.module.scss`)

- Tokens only (Rule 3): typography, colors, code/quote backgrounds via `var(--…)`.
- **No `margin` (Rule 4).** Inter-block vertical rhythm comes from a flex-column container with a `gap` token on the root; list/quote internal spacing likewise via `gap`/`padding` tokens, never margins. (A rich-text renderer's internal block spacing is its own typographic responsibility — implemented Rule-4-compliantly with `gap`, not by positioning.)
- `:focus-visible` not needed (non-interactive in Slice 1).
- Dark-theme-safe (component tokens default to primitives where colors are introduced).

## Testing

Pure functions ⇒ exhaustive, cheap unit tests, one `*.test.ts(x)` per module:

- **marks:** equal (incl. link href + order-insensitivity), has, with/without (link href replacement), toggle.
- **inlines:** normalize (merges adjacent equal-mark runs, drops empties, guarantees ≥1 run), runsText/length, sliceInlines at/inside/spanning run boundaries, mapMarksOverRange splits runs correctly and re-normalizes.
- **position:** blockLength, findBlockIndex, clampPoint, comparePoints (same block + across blocks), orderedRange, isCollapsed.
- **transforms:** insertText (start/mid/end of run, empty block, mark inheritance), deleteRange (within run, across runs, across blocks with merge, collapsed = no-op), splitBlock (start/mid/end; list/heading continuation), mergeBlockBackward (first block = no-op), applyMark/removeMark/toggleMark (partial vs full coverage, run splitting + re-normalize), setBlockType.
- **renderDoc:** each block type → correct element; heading level; mark nesting order; consecutive items → one `<ul>/<ol>`; depth nesting; empty doc → nothing; stable keys.
- **RichText:** renders a sample doc, `ref` forwarded, `className` merged, passthrough props.

## Repo invariants (Core invariant checklist)

- `RichText.test.tsx` (Rule 1) + the per-engine-module tests.
- Demo page `packages/playground/src/pages/components/RichTextDemo.tsx` + wire into `App.tsx`, `navItems.ts` (Display group), `ComponentsIndex.tsx`. The demo renders sample docs AND has buttons that apply transforms (e.g. toggle a mark over a fixed range, change a block type) to a shown doc, re-rendering via `<RichText>` — proving the engine works without a full editor.
- `src/index.ts` re-export (Rule 5).
- Manifest `RichText: 'Display'` in BOTH `src/_meta/manifest.ts` and `scripts/generate-manifest.mjs`, then `npm run build:manifest` (drift test).
- `AGENTS.md` TL;DR section + `@remarks` anti-patterns in JSDoc.
- No i18n: a read-only renderer ships no user-facing strings (empty doc → renders nothing).

## Out of scope (Slice 1)

- Any editing / input handling / contentEditable / selection mapping (Slices 3–4).
- HTML/markdown serialization (Slice 2) — consumers build a `RichDoc` directly for now.
- Multi-line `code_block` semantics beyond plain split; tables, images, mentions, color/highlight marks.
- Undo/redo history, collaboration.

## Anti-patterns (for JSDoc `@remarks`)

- ❌ Using `<RichText>` for plain text → use `<Text>`.
- ❌ Expecting `<RichText>` to edit → it's read-only in Slice 1; the editable `<RichTextEditor>` is a later slice.
- ❌ Mutating a `RichDoc` in place — every transform is immutable; use the returned doc.
- ❌ Storing positions as raw integers — use `{ blockId, offset }` so they survive edits to other blocks.
