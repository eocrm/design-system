## 1. #679 — Tooltip overflow

`Tooltip.module.scss` `.content` caps `max-width: 240px` with no
`overflow-wrap`, so a URL runs past the bubble. Add `overflow-wrap: anywhere`
to `.content` (DropdownMenu and DataTable already use it). Regression test in
the style the repo already uses for CSS guards (builder's call).

## 2. #682 — Image backdrop

New prop `background?: 'muted' | 'none'`, **default `'none'`** (dpws).

- `'none'`: the loaded state paints no backdrop — transparent assets and
  `contain` / `scale-down` / `none` letterboxing show the parent surface.
- `'muted'`: today's `--image-bg` behind the loaded image.
- Loading skeleton and error tile are unchanged in both modes (they keep
  their muted fill).

Visible change for existing consumers (letterboxing / transparent images
lose the grey square on upgrade). Ships as a patch (release default); call it
out in the PR body and the component doc. eocrm is the only consumer.

Docs: props table regenerated; TL;DR mentions the default; demo gets a
transparent-logo example with both values.

## 3. #683 — Tour click cue

**Today:** `.spotlight[data-interactive]` draws a 1px accent outline pulsing
outward (`tour-pulse`). Reported as unnoticeable.

### The wave recipe (shared with Highlight, §4)

dpws picked variant "B" from live mockups:

- Two staggered waves growing OUTWARD from the shape's edge and fading.
- Each wave: a ring with a solid 2px outer edge (border) and a gradient
  fading inward toward the shape — mockup recipe
  `border: 2px solid C; box-shadow: inset 0 0 22px 5.5px rgba(C, .55)`.
- Travel: from the edge (inset 0) to 20px outside it, opacity ~0.9 → 0,
  corner radius growing with the ring (shape radius + travel).
- Cycle 2.2s, `cubic-bezier(.2,.6,.4,1)`, infinite; the second wave starts
  half a cycle later.
- Reduced motion: no waves; one static 2px ring at the edge.

Shared as a SCSS mixin in `src/styles/` (parameterised by colour custom
property), so Tour and Highlight can't drift. **(call)**

### Tour specifics

- Drawn by the spotlight element's `::before` / `::after` (the spotlight is a
  fixed overlay, nothing clips an outward ring). `pointer-events: none`.
- Colour: white — a shared token that is white in both themes (builder
  picks, e.g. the on-accent/inverse fg; the scrim is dark in both themes).
- Values are `--tour-*` tokens in `Tour.tokens.scss`; raw durations get a
  comment like today's `--tour-pulse-duration`.
- Replaces `tour-pulse` and the `--tour-pulse-*` tokens (removed, not left
  dead). Check playground / docs references.
- **When the cue shows:** every modal step with `interactive: true` — same
  condition as today's `data-interactive`. **(call)**

### Card on click-to-continue steps (dpws: option 1)

Applies exactly when a click on the target advances the tour:
`advanceOn: 'click'` AND (`interactive: true` in modal mode, or `modal={false}`).

- Next/Done renders `variant="secondary"` instead of primary.
- A muted line above the button row: i18n key `tour.clickHint`
  — en: "Click the highlighted element to continue", ru: "Нажмите на
  выделенный элемент, чтобы продолжить". Styled like `.progress`. Plain
  content of the dialog (read with the step), not a live region.
- Next still works (escape hatch).
- No per-step `cue` opt-out (not requested). **(call)**

## 4. Highlight — outward waves on an overlay layer

dpws: waves go OUTSIDE the element, drawn on a separate overlay layer so
they are never clipped (a DashboardCanvas cell is `overflow: auto` and the
widget fills it; Table's scroll wrapper clips; later grid siblings would
paint over an outer shadow on the element itself).

### Rendering

- Highlight still renders no wrapper around the child: it clones the child
  to attach a ref (and `data-highlight` as today's test/consumer hook). It
  **no longer adds a class or touches the child's `outline` / `box-shadow`**
  — so Card elevation and tone stripe stay visible during a highlight. The
  CSS-class contract ("child must forward `className`") goes away; the child
  must still forward `ref` to a DOM element.
- While active (stages `on` / `fading`), Highlight portals one decorative
  element (`aria-hidden`, `pointer-events: none`) to `document.body`:
  position `fixed`, sized and placed over the child's **visible** rect,
  border radius copied from the child's computed `border-radius` (read at
  activation).
- **Visible rect** = the child's rect intersected with every clipping
  ancestor's rect (overflow ≠ visible) and the viewport. Fully clipped →
  the overlay is hidden (`display: none` / `visibility: hidden`). Partially
  clipped → the ring wraps the visible part. The waves themselves extend 20px
  beyond that rect unclipped. Builder may use Floating UI's helpers
  (`getClippingRect` / `platform`) — already a dependency.
- Tracking: Floating UI `autoUpdate(child, overlay, update)` (scroll on any
  ancestor, resize, layout shift) — same as Tour's Spotlight.
- **z-index:** `--highlight-z: calc(var(--z-app-chrome) - 1)` — above page
  content, below fixed app chrome (so the top bar covers the ring when the
  child scrolls under it) and below dropdowns. A child inside a Modal /
  Drawer / Popover / Tour host elevates with it: `useInOverlay(childRef,
active)` → `var(--z-overlay-floating)`. **(call)**

### Look and lifecycle

- Steady ring: 1px, just outside the child's edge, in the colour (dpws —
  approved from the outward mockup). Was 1px inset + inset glow; the glow
  goes. Waves keep the §3 recipe (2px wave edges).
- Waves: the §3 recipe, run continuously while `stage === 'on'`
  (not a fixed entry count); so `duration={Infinity}` waves until `active`
  goes false. **(call)** On `fading`, ring + waves fade out over
  `--highlight-fade`; `onDone` timing unchanged (FADE_MS mirror stays).
- Reduced motion: static 1px ring, no waves, no fade — `onDone` straight
  after `duration` (unchanged).
- `scrollIntoView` / `focus` behaviour unchanged.

### Colour

New prop `color?: PaletteColor` (dpws). Unset = today's accent
(`--ring-accent`). Set = ring and waves use `--color-palette-<color>-fg`
(the saturated half, readable in both themes) via the existing
`paletteTokens()` helper, as an inline custom property on the overlay
(not on the child — nothing on the child changes). Wave alpha via
`color-mix` as `Highlight.tokens.scss` does today.

### Docs

Rewrite the visual description, remove the "replaces box-shadow/outline" and
inset-glow caveats, add the overlay/clipping/z-index notes and a `color`
example; demo shows a Card, a DashboardCanvas widget and a Table row, plus a
few palette colours.

## 5 + 6. #684 / #685 — tour target inside a floating surface

### Current-target marker

Tour marks the **current step's found target** with
`data-tour-current-target` on every step (modal and non-modal, interactive
or not), removed on step change / close. The existing
`data-tour-active-target` (interactive modal steps — elevates surfaces
opened FROM the target) is unchanged.

A shared helper in `_internal/overlay`, e.g.
`tourPointsInto(panel, trigger): boolean` — true when the element carrying
`data-tour-current-target` is inside `panel`, or inside / equal to
`trigger`.

### #684 — the tour doesn't dismiss a surface it points into (dpws: option 1)

While `tourPointsInto(panel, trigger)`:

- **Pointerdown path:** a pointerdown anywhere inside `[data-tour-portal-root]`
  (card, buttons, the dimmed-page blockers) is not "outside". **(call:** the
  whole tour layer, not only the card — so a stray scrim click doesn't break
  the next step; Skip leaves the surface open, like Done.)
- **Focus-leave path:** surfaces that close when focus leaves them
  (DatePicker, DateRangePicker — `handleInputBlur` / `isInsidePicker`;
  TopBarSearch `handleBlur`) treat focus moving into `[data-tour-portal-root]`
  as not leaving. Needed because Tour moves focus to the card on every step.
  **(call)**
- Applies to every `useInOverlay` surface: DropdownMenu, Popover, Select,
  DatePicker, DateRangePicker, TimeField, Rail.Group flyout, TopBarSearch.
- Once the current target is elsewhere, both paths behave as today.
- Escape unchanged. If the last step points into the surface, Done ends the
  tour and leaves the surface open (dpws accepted).

Issue repro that must pass: step A (interactive, `advanceOn: 'click'`,
target = DropdownMenu trigger) → click opens menu, tour advances → step B
(target = menu content) → Next → step C (target = item in the menu) is found.

### #685 — surface containing the target sits under the scrim

A floating surface whose panel **contains** the `data-tour-current-target`
element is not elevated above the tour: its z-index becomes
`calc(var(--tour-z) - 1)` — under the scrim, but still above `--z-modal`, so
a menu opened inside a Modal stays above the Modal. **(call)** A surface
opened FROM an interactive target (target = trigger, not inside the panel)
elevates exactly as today.

- Mechanism: builder's choice — CSS `:has([data-tour-current-target])` on
  each surface's elevated rule, or JS in the shared hook. Must hold for every
  `useInOverlay` surface.
- Interactive step on an item inside the surface: the cutout is
  pointer-transparent, so the item stays clickable. Test it.
- **Re-measure after enter animation:** `Spotlight` re-measures on
  `animationend` / `transitionend` (capture listener on `document` while a
  target is set, calling the same `update`). Fixes the cutout measured mid
  scale-in.

## 7. #686 — DashboardCanvas section highlight (dpws: option 1)

New props on `DashboardCanvas`:

- `highlightedSectionId?: string | number`
- `onSectionHighlightDone?: () => void`

The canvas wraps the matching section band (the element registered in
`bandsRef`) in `<Highlight active scrollIntoView>` — same visuals and timing
as `Highlight` (default duration), **no `focus`** (eocrm opens the title for
rename on add; a focus move would fight it). Semantics mirror Highlight's
`active` / `onDone`: a change to a new id (or unset → id) starts one run;
`onSectionHighlightDone` fires after the fade and typically clears the id;
clearing it early stops without the callback. An id with no matching section
does nothing (dev warning). The band's existing ref (`bandsRef`, drag) must
keep working through Highlight's ref merge.

Docs + demo: "Add section" example that highlights the new band.

## 8. #687 — DashboardWidget `actionsReveal` (added later; dpws: "include 687")

New prop `actionsReveal?: 'always' | 'hover'`, default `'always'`. With `'hover'`:

- Actions are hidden with **`opacity` only** — not `visibility` / `display` —
  so they stay in the tab order and keep their layout width (no title/meta
  jump). **(call:** the issue suggests "opacity/visibility"; `visibility:
hidden` removes them from the tab order, breaking "Tab into the card
  reveals them".)
- Revealed while the widget is `:hover` or `:focus-within`.
- Always visible under `@media (hover: none)`.
- Kept visible while a menu/popover launched from an action is open: the
  widget `:has([aria-expanded='true'])` inside its actions slot (DS
  DropdownMenu / Popover / Select triggers set `aria-expanded`). A `Modal`
  launched from an action needs nothing: its scrim covers the widget and
  focus returns to the action on close, which reveals it via
  `:focus-within`. **(call)**
- Opacity transition uses an existing `--transition-*` token; reduced
  motion: no transition.
- `pointer-events` stay on (a pointer reaching the action has hovered the
  card anyway).

Docs: prop row + a "Quiet headers in view mode" example; demo toggle.
Tests: `data-actions-reveal` hook on the widget, SCSS guard for the
opacity-only rule + the hover/focus-within/has/hover-none selectors, and the
actions stay in the tab order (focusable) when hidden.

## 9. #688 — Modal.Footer wraps instead of clipping (added later; dpws: "and issue 688")

`.footer` in `Modal.module.scss` is `display: flex` + `justify-content:
flex-end` with no `flex-wrap`, so actions wider than the dialog push the
first button past the left edge. Add `flex-wrap: wrap`: overflowing actions
wrap onto another row, keeping the footer's alignment (right-aligned for
`end`). Same fix in `Drawer.module.scss` `.footer`, which has the identical
rule. **(call:** fix the sibling with the same bug; Accordion `.actions`,
OptionsPicker `.footer` and Rail `.footer` are different layouts and stay
as they are.)

Tests: SCSS guard per file. Demo: Modal size `sm` with three long actions.
