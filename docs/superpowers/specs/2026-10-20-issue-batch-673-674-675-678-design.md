# Issue batch #673 / #674 / #675 / #678 — design

One branch, one PR (dpws chose to bundle all four). Three are small fixes; #675
is the feature that needed decisions.

## #673 — inline-only custom properties read without a fallback

`Button.module.scss` `.palette` reads `var(--button-palette-bg)` /
`var(--button-palette-fg)` with no fallback; the properties are only ever set
inline. eocrm's dist check requires every fallback-less `var()` to be declared
by a loaded stylesheet.

**Scope (dpws decision): the whole library, plus a guard.** A scan found 24
such properties across 11 components (Button, Calendar, Chart, EntityChip,
IconPicker, IconTile, PillMenu, QrCode, TreeView). eocrm's check will trip on
each as soon as a lazy chunk loads that component.

**Fix:** give every fallback-less read of an inline-only property a neutral
fallback inside the `var()` — `transparent` / `currentColor` for colours,
`0` / `auto` / `none` / `1` for geometry, as fits the property. **Not** a
default declaration in the rule: several are set on an ancestor and read on a
child (e.g. `--tree-view-level` on `.item`, read on `.row`), where a local
declaration would shadow the inherited inline value. The fallback never paints
in practice.

**Guard:** a Node unit test that scans every `src/**/*.scss`, collects every
custom-property declaration, and fails on any `var(--x)` with no fallback
whose `--x` no stylesheet declares — naming file, line and property.

## #678 — EntityChip clips label descenders

Root cause: `.chip` uses `line-height: 1` (`--entity-chip-line-height`), and
labels use `overflow: hidden` for ellipsis. At line-height 1 the line box is
shorter than ascent+descent, so `overflow: hidden` clips descenders.

The issue reports only the segmented chip (`.core > .label`, always clipped),
but the same combination exists on the other truncating label rules
(`EntityChip.module.scss` ~lines 118, 157, 181 and 254 at the time of writing). **Fix every
`overflow: hidden` + `text-overflow: ellipsis` label rule in the file**, not
just the reported one.

**Fix:** replace `overflow: hidden` with `overflow-x: clip; overflow-y: visible`
(logical equivalents if the file uses them) on those label rules, keeping
`text-overflow: ellipsis` and `white-space: nowrap`. Do **not** use
`padding-block` / a taller line-height: it changes chip height and breaks the
#591 outer-box alignment. Browser floor: evergreen (Chrome 90+, Safari 16+,
Firefox 81+) — eocrm is a 2026 web app; no older-engine fallback _(my call)_. `labelEllipsis="start"` (#593) must still ellipsize
at the start. Verify visually in the playground (Playwright, port 8090+):
"Evening yoga — beginners" segmented, plus a truncated long label, both with
intact descenders and a working ellipsis.

## #674 — TreeView hover signal

**Add** `onHoverChange?: (id: string | null) => void` to `TreeViewProps`.
Fires with the node id when the pointer enters a **node** item's `.row` (the
whole box in chart view, the whole row in list view — the same element the
existing `:hover` styles target), and with `null` when it leaves. Status rows
(loading / error / overflow) do not fire. Visual/pointer only — no ARIA, no
effect on focus or selection (matches `highlightedIds`).

**Rejected:** the issue's `highlightOnHover`. The consumer must still supply
the ancestors, so it saves one `useState` while adding a second highlight
path that can conflict with `highlightedIds`.

Builder's call: avoid a `null` flash when moving directly between adjacent
rows only if it is cheap; it is not required.

## #675 — OptionsPicker async `loadOptions`

### Why

eocrm filter strips use `OptionsPicker` for member filters (Owner, Member).
Options are passed up front and filtered client-side; the roster is one page
of 100, so members past it can't be found. Need server-side search.

### Decisions (dpws)

1. **Selected rows stay pinned at the top** in async mode, whatever the
   query, so the user can always untick them.
2. **Async footer shows "N selected"** (new i18n key, en + ru). No total.
   `footerCount` is not called in async mode; its signature is unchanged.
3. **Flat options only.** `loadOptions` returns `OptionsPickerOption[]`; no
   groups in async mode. Can be widened later without a breaking change.

### API

On `OptionsPicker.Content` (the flat branch of the options/groups union gains
a third, async branch):

- `loadOptions?: (query: string, signal: AbortSignal) => Promise<OptionsPickerOption[]>`
- `selectedOptions?: OptionsPickerOption[]` — labels for currently selected
  values the component hasn't seen in any server answer (e.g. values restored
  from a URL). The consumer already has these to render its trigger.
- `searchDebounceMs?: number` — default matches Select (250).

On the Root (dpws decision): **`onApply` gains a second argument** carrying
the selected options — multi: `onApply(values: string[], options:
OptionsPickerOption[])`; single: `onApply(value: string | null, option:
OptionsPickerOption | null)`. Non-breaking (existing one-arg callbacks still
type-check). Options come from the label cache (sync mode: from `options` /
`groups`); a value with no known label yields `{ value, label: value }`. This
is how eocrm learns the label of a member found by server search, for its
trigger and for the `selectedOptions` it passes on the next open. Because the
cache lives in Content but `onApply` is called from Root's `commit`, Content
passes the resolved options into `commit` (builder's call how).

Mutually exclusive with `options` / `groups` at the type level where cheap;
otherwise mirror Select: if both `options` and `loadOptions` arrive,
`loadOptions` wins and a dev-only `console.warn` fires.

### Behaviour

- **Fetching:** reuse Select's `useAsyncOptions` (debounce, abort on new query
  and unmount, error, `retry`, `loadedQuery`). Move it to a shared location
  both components import (my call: `src/components/_shared/` or wherever the
  repo keeps cross-component hooks — follow existing convention). Its
  `SelectOptions<T>` type coupling must be loosened so OptionsPicker can use
  it without importing Select types awkwardly. Select behaviour must not
  change; its existing tests are the guard.
- **Fetch on every open** with query `''` (the panel already resets its
  filter on open), so a reopened panel shows fresh data — not Select's
  `hasOpenedOnce` gate. Drive the shared hook's `enabled` from "panel is open
  now"; Select keeps passing its own gate, so its behaviour is unchanged.
  No `loadOnOpen` prop — YAGNI. _(my call)_
- **Search:** in async mode the server's answer replaces the list; no
  client-side filtering on top of it. The search input is always shown in
  async mode (`searchable={false}` + `loadOptions` is meaningless; warn in dev
  or ignore — builder's call, document it).
- **Label cache:** the component remembers `value → option` from every server
  answer it receives while mounted, plus `selectedOptions`. Pinned rows use
  this map. A selected value with no known label renders its raw `value` as
  label (never blank, never crash) — documented as "pass `selectedOptions`".
- **Pinned rows — snapshot model _(my call)_:** the pinned set is the
  selected values **as of panel open or the last settled query change**, in
  selection order, rendered first. Rows never move under the pointer:
  ticking a server row leaves it where it is; unticking a pinned row leaves
  it pinned (unticked). The snapshot is retaken when the query changes, so
  newly ticked values become pinned on the next search and unticked ones
  drop out. A pinned value that also appears in the current server answer is
  **not** repeated below. Single mode: the selected value is pinned (picking
  commits and closes, so no snapshot question).
- **Keyboard:** pinned rows join the existing arrow-key order, before the
  server rows.
- **States:** loading, error-with-Retry, and empty ("no results for X") rows
  modelled on Select's `Loading` / `Error` / `Empty`. Empty only shows when
  the server returned nothing for the settled query (use `loadedQuery`, as
  Select does, to avoid "No results" during the debounce window). Pinned rows
  remain visible in all three states.
- **Footer (multi):** "N selected" via new i18n key; Cancel/Apply unchanged.
- **Sync mode is unchanged.**

### Accessibility (Hard rule 10)

Loading / error / empty are changes while the user's attention is on the
search input → component-owned live region: one visually-hidden
`role="status" aria-live="polite"` span, **rendered unconditionally** in the
panel, text set from an effect. Follow Select's `Listbox` pattern (#495): the
visible state rows are `aria-hidden` so readers don't hear them twice. Read
`.claude/skills/transient-state-a11y/SKILL.md` before implementing and record
the decision in the component's doc.

### Tests

jsdom (`OptionsPicker.test.tsx`), fake timers as Select's async tests do:
first fetch on open with `''`; debounced fetch on typing; stale response
discarded (abort); pinned selected rows present when the answer omits them,
labelled from `selectedOptions` and from a previously seen answer; no
duplicate row when the answer includes a selected value; footer "N selected"
and `footerCount` not called; error row + Retry re-fires; empty row only
after settle; live region text for loading/error/empty; single mode commits;
`onApply`'s second argument carries labels for a value picked from a search
answer (async) and for sync options, and `{value, label: value}` for unknowns.
Shared-hook move: existing `useAsyncOptions.test.ts` moves with it.

## Non-goals

- Async groups, pagination / infinite scroll, `loadOnOpen=false`, a label
  cache for Select (still Phase 8+), `highlightOnHover`.
